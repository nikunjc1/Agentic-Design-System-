## Tooltip color fix, round 2 - the real root cause

The user reported the same "tooltip needs to be dark in light mode / light in dark mode" issue twice more after the fix above, despite it verifying correct on every fresh check. Root cause: `var(--text-hi)` and `var(--graphite-900)` - the pair the first fix reused for the inversion, because their *default* values happen to already form an inverted near-black/near-white pair - are both wired into this site's real, working per-theme brand color customization (`shell.js`'s `applySavedColorsForTheme`, driven by `localStorage["ads:text-colors"]`/`["ads:bg-colors"]`, saved from Foundations). A custom "Text Hi" or "Background Secondary" saved for either theme silently overrides those variables and breaks the inversion this component depends on - invisible to any fresh/clean browser check (which is exactly why my Playwright verification kept passing), but very real in an actual browser carrying saved customizations.

Fix: added two new tokens to `theme.css`, `--overlay-invert-bg`/`--overlay-invert-text`, holding the same default values as before but declared independently of the brand customization system - `applySavedColorsForTheme` never touches them. Switched `.tooltip-demo-bubble`, `.tooltip-demo-description`, and `.tooltip-demo-arrow` (in `shell.css` and the matching Copy Code/Copy Prompt emission in `tooltip-detail.js`) to the new tokens. Also caught and fixed a real leftover bug while in there: the Copy Prompt text still described the pre-fix colors (`Background var(--graphite-700), color var(--text-hi)`) from before the very first color fix - never updated at the time.

Verified with an adversarial test a clean check can't catch: saved deliberately-wrong custom colors to `localStorage` (a light-theme "Text Hi" of light gray, a dark-theme one of near-black, plus unrelated magenta/green "Background Secondary" values) and reloaded - the tooltip still rendered correctly inverted in both themes, proving the fix no longer depends on what's saved there at all.

## Global — sidebar had no active item at all on every component's own type/detail page

Reported as "links are not working, pages aren't linked to each other" and separately "when I'm scrolling and selecting a tab, its position in the left-side nav isn't fixed/updating." Rather than trust either description literally, audited the actual link graph first: every `<a href>` in every one of the 157 pages resolves to a real file, every `href="#hash"` resolves to a real `id` on its target page, every dynamically-constructed `window.location.href` navigation (the `.system-card`/`.button-type-card` click handlers used by all 62 listing pages) resolves to a real file, and every "← Back to X types" link on all 69 detail pages points at its own correct listing page. No actual broken or misdirected links anywhere - the link graph itself is sound.

The real bug was in `shell.js`'s `markActiveLink()`, which powers both complaints at once. It only ever matched the current page's own filename against the sidebar's `<a class="nav-link">` hrefs - but the sidebar only links to each component's *listing* page (`table.html`, `components.html#button`), never to its type/detail pages (`table-default.html`, `button-primary.html`, `select-dropdown.html`, etc.), since those are only reachable via the dynamic card-click navigation above. So on all 69 of those pages - exactly the pages a user actually lands on to configure and read about a component, i.e. most of the time spent on this site - `markActiveLink()` matched nothing at all: no sidebar item was ever marked `.is-active`, and the page-load `scrollIntoView` that's supposed to bring the current page's item into view never ran either, since it's gated on a match existing. The sidebar just sat at whatever scroll position it last had, with nothing highlighted - which reads exactly like "the tab I selected isn't shown, and its position doesn't update."

Confirmed with a full 157-page sweep before fixing: `.nav-link.is-active` existed on 88 pages and was completely absent on the other 69 (every `-default.html` page plus the 6 Button variants, Select Dropdown, and Input Text Field).

Fixed by adding a third fallback to `markActiveLink()`: when no sidebar link matches the current page directly, read the current page's own `.back-link` href (verified above to always be correct) and match the sidebar link against *that* instead - reusing an already-correct value rather than re-deriving the listing filename from the current page's own name, which isn't safely reversible (both the component name and the type key can contain hyphens, e.g. `date-picker-default.html`). Re-swept all 157 pages after the fix: every page now has exactly one `.is-active` sidebar link, correctly scrolled into view (verified on `table-default.html`, `button-primary.html`, `select-dropdown.html`, `date-picker-default.html`), and this holds even when the containing nav group was previously collapsed by the user (tested by forcing `ads:nav-collapsed:components=1` in storage first) - `initCollapsibleGroups` force-expands whichever group the now-correctly-matched active link lives in.

## UX pass - findings from testing the portal as a user, not just reading the code

Ran an actual hands-on session with Playwright (search, the welcome modal, phone-width viewport, keyboard/focus behavior) instead of only auditing markup, then confirmed each finding with the user (with selectable options) before implementing anything. Four real gaps found and fixed; one initial finding about the welcome modal was itself wrong and corrected before implementing - see below.

**Welcome modal reappeared on every visit.** `welcome.js` never recorded that a visitor had already seen and dismissed it - reloading or revisiting `overview.html` always reopened it, with no way to make it stop. Fixed by writing `ads:welcome-seen` to localStorage inside `closeModal()` (which already runs on every dismissal path - choosing a project path, Escape, or backdrop click) and skipping `openModal()` entirely when that flag is already set.

*Correction made before implementing:* Escape-to-close and backdrop-click-to-close were initially reported as broken too, based on an automated check that looked for a `hidden` attribute on the wrong element (`.welcome-modal` itself, a non-hidden child, instead of its parent `.welcome-overlay`, which is what actually gets `hidden`). **Global "/" search shortcut broke the welcome modal's focus trap.** The modal correctly traps Tab/Shift+Tab inside itself while open, but `shell.js`'s document-level "/" handler only skipped itself for a native `dialog[open]` - the welcome modal is a plain overlay div toggled via a `hidden` attribute, not a `<dialog>`, so it wasn't recognized and "/" could still yank focus out to the sidebar search behind an `aria-modal="true"` dialog. Verified each fix individually (persistence across real navigations, not Playwright's `reload()` which can restore from bfcache and mask a missing localStorage write; drawer open/close via toggle/backdrop/Escape/nav-click; empty state appearing and clearing correctly) and re-ran the full 157-page sweep afterward: 0 console/page errors, every page still has exactly one `.nav-link.is-active`.
