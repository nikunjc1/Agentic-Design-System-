Foundations · Shadows

Shadows

Shadow is an elevation system, not decoration - it answers one question: how far above the surrounding surface does this sit? Use the smallest elevation that communicates the right layer, and never rely on shadow alone for focus, selection or state.

Shadow philosophy

The elevation character every card, dropdown, panel and overlay in this system follows. Balanced is the global default unless your product type above recommends otherwise.

Elevation hierarchy

Semantic elevation layers, not arbitrary box-shadow values - each answers "how far above the surface does this sit?"

Base Page, section, table rows - same surface, no elevation needed None
Raised Standard cards, slightly raised controls, sticky elements XS · SM
Dropdown / Popover Clearly elevated above the content beneath - menus, date pickers MD
Floating / Drawer Floating panels, toolbars, side drawers LG
Modal Dialogs and modals - pair with a backdrop and surface contrast, not shadow alone XL
Major overlay Complex overlays and large floating experiences - use sparingly 2XL

Component defaults

Button Default none · hover XS · pressed none - don't make every button look elevated None / XS
Input Default none · focus uses a visible ring, never shadow alone None
Card Standard SM · interactive: default SM → hover MD → pressed XS SM
Dropdown / Popover Should clearly appear above the content beneath it MD
Tooltip Stays visually lightweight - never heavier than a card SM
Modal / Dialog Pair with backdrop + surface contrast, not shadow alone XL
Drawer / Bottom sheet Side drawer LG · mobile bottom sheet XL - edge touching the viewport stays unrounded, not unshadowed LG / XL
Floating action button Default MD · hover LG · pressed SM SM / MD / LG
Sticky header None until scrolled, then XS - never a permanent strong shadow None / XS
Table Borders and row separation do the work - avoid shadows between rows None
