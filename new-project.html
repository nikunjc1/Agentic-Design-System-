Design System · Onboarding

New Project Mockup

Owner: Design System Team · Version: v3.4.0 · Changelog: not yet tracked

The flow a user with no projects goes through to get a working design system: a choice, a short wizard, generation, and either a success or a partial-failure landing. Shown here as static reference screens (this portal has no backend to actually run generation) - every state below is grounded in the build brief's own corrections (a modal only ever carries the choice; the flow itself is a routed, resumable wizard).

1. Entry modal - shown once, choice only

Appears only for a user with zero projects. Everyone else lands on the project Listing page; creation stays reachable from a persistent "+ Create New Design System" action rather than reappearing as a blocking modal.

Create your first Design System

Set up your project details. These generate your design system, AI context, NPM package, and Markdown documentation.

✦ Create New

Start from a few project details · ~3 minutes

  • Accessibility - dismissible via close button, Escape, and backdrop click; focus moves to the first interactive element on open and returns to the trigger on close; role="dialog", aria-modal="true", labelled by its own title.
  • Not shown again in the same session after dismissal, but the create action remains available at all times from the Listing page.

2. Wizard structure - routed, resumable, autosaved

A modal cannot hold this many fields accessibly (no deep-linking, no browser back, total work loss on accidental dismiss, unusable on mobile) - so the flow itself lives at its own routes. Only Step 1 is required.

1. Project details Name, product type, email, designation Required
2. Context Product description, users, market, direction Skippable
3. Review Generation scope preview —

No separate Brand or Foundations steps

Brand color already lives on the Colors foundation page, and Typography / Spacing / Accessibility already have their own foundation pages in this portal - re-collecting them here would just duplicate what those tabs already own. The wizard only asks for what doesn't exist anywhere else yet.

3. Step 1 - Project details

Used for your package name and MD files - slug: insureedge-3-0

SaaS · Enterprise · Consumer · Internal tool · Other

Use a different email

  • Email is prefilled, never re-requested - the user is already authenticated, so asking again is redundant entry (WCAG 2.2 SC 3.3.7). Shown read-only with a "use a different email" affordance for the invite/unauthenticated case only.
  • Designation is not cosmetic - it sets the default landing tab (Designer → Foundations, Developer → Tokens & Code, PM → Overview) and the default MD export tier. "Other" requires a free-text field before continuing - never restricted to a fixed list of job titles.
  • Validation - project name 2-60 characters, must produce a valid, URL-safe npm slug; the derived slug is shown live and collisions with existing projects in the org are flagged immediately, not on submit.

4. Step 2 - Product context (skippable, high value)

This becomes the project's AI Context. Skipping it is allowed, but the field states plainly what's lost by skipping.

  • Continues if the user navigates away or closes the tab; completion is announced via an in-app notification (and email past 2 minutes).
  • Cancel is available until the publish step; cancelling discards the partial system and returns to the wizard with inputs intact.

Component Guide

Accessibility

  • Modal and wizard: focus moves in on open, returns to trigger on close; Esc dismisses; focus trapped while open (SC 2.4.3, 2.1.2).
  • Each wizard step is a landmark with a heading; progress is announced on change (SC 1.3.1, 4.1.2).
  • Prefilled email is never re-requested (SC 3.3.7 Redundant Entry).
  • Generation progress uses aria-live="polite", stage-level announcements, no timeout (SC 4.1.3, 2.2.1).

Related

Brand color is configured on Foundations · Colors, and Typography / Spacing / Accessibility target on their own foundation pages - not repeated in this wizard. Generation feeds directly into NPM Package (Step 3's optional NPM checkbox), MD Export (the generated documentation), and History (generation always creates Version 1.0.0).
