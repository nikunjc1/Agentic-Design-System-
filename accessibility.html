Guidelines · Accessibility

Accessibility

What this system already does for you on every page, without being asked - and, just as importantly, what it doesn't do yet. WCAG 2.2 AA is the baseline referenced throughout.

Automatic on every page

Injected sitewide by experience.js - a page doesn't opt in, and can't opt out.

Skip to content A "Skip to content" link is prepended to every page, targeting a real, focusable <main> landmark 2.4.1
Heading structure Every visually-styled "panel title" is retrofitted into a real <h2>, not left as a plain, non-semantic paragraph 1.3.1
Page outline An "On this page" navigation landmark is auto-built from a page's real headings once there are more than two 2.4.5
Current page The active sidebar link carries aria-current="page" automatically 4.1.2
Icon-only buttons Any icon-only button's title attribute is copied to aria-label automatically, so it has a real accessible name 4.1.2
Clickable cards A card that navigates on click is a real <a> element, not a div with a click handler and no keyboard path 2.1.1
Horizontal scroll regions Any horizontally-scrolling comparison table is marked role="region" with a descriptive label 1.3.1

Focus

A single semantic token, --color-focus-ring (Colors), backs the sitewide focus-visible convention - 76 of 82 focus outlines sitewide use it directly; the other 6 (destructive/success/info contexts) deliberately use that context's own color instead. Keyboard-only focus (:focus-visible), not every mouse click, is what triggers it.

Motion

Every transition and animation sitewide resolves to one of six shared motion tokens (Motion isn't yet its own Foundation page, but the tokens exist in theme.css). Under prefers-reduced-motion, animation and transition durations sitewide collapse to near-zero - a user who has asked their OS to reduce motion gets that everywhere in this system, not page-by-page.

Touch targets

Icon buttons and nav links are 32px by default (already above WCAG 2.2's 24px AA minimum) and grow to 44px automatically on a coarse pointer (touch), meeting the AAA-level target size as well wherever it actually matters - a touch device, not a mouse.

Color contrast

Every one of the 32 color swatches on Colors carries a live, real WCAG contrast badge - AA/AAA (4.5:1 / 7:1) for anything used as text, and a separate 3:1 Non-text check (WCAG 1.4.11) for Control Border, which isn't text and was never correctly held to the text thresholds. Opening any swatch's picker also previews it under protanopia, deuteranopia and tritanopia (a standard simplified simulation, not a clinical-grade one) - a color choice that only works when swatches otherwise differ can be caught before it ships, not after. See Colors for the live checker itself.

Localization and preferences

Theme, density and direction (RTL) are each a real, live, sitewide toggle (Settings), persisted per browser and synced instantly across any other open tab of this system - not a per-page setting you'd have to repeat.

Known gaps - not yet done

Said plainly, not glossed over:

ARIA depth per component Table and Modal have rich, component-specific ARIA; simpler components mostly rely on shared shell chrome - not independently audited component-by-component Uneven
200% zoom / reflow Not individually verified per component across the 63-component library Unverified
Text spacing override (1.4.12) Not tested against a user style sheet that overrides line-height/letter-spacing/word-spacing Unverified

Foundation editor state model

Every Foundation editor uses the same words - saved, previewed, applied, exported - but what each one actually does differs by section; this is the one place that distinction is written down. Draft: what's in the field right now, not yet written anywhere. Preview: this page's own swatches/sample text updating instantly from the draft value alone, e.g. renderScaleChips() (foundations.js:339) re-rendering Brand's scale on every keystroke - true on every editor, independent of save or apply. Auto-save: written to localStorage the moment a field changes (input/change), independent of any button - see wireSaveState's handleEdit (foundations.js:54). Apply: the saved value actually changing what the current tab renders right now, instead of only taking effect on the next page load. Export: what Markdown/token export reads - always the latest auto-saved value, whether or not Apply has run.

Radius, Typography (font) Auto-saves AND auto-applies sitewide on every edit - window.ADS_applySavedRadius / window.ADS_applySavedTypographyFont (shell.js:190-191) run immediately. Its Save button is a confirmation, not a gate: nothing is withheld if you never click it. Auto-save + auto-apply
Colors (Brand, Surface, Status, Neutral) Auto-saves on every edit (same wireSaveState mechanism), but Apply to the current tab only runs when you click "Save ... color/scale" - other already-open tabs and the next reload pick up your edit regardless of whether you clicked it. The status line under each button now says "Applied to this page" instead of "Saved just now" so it can't be read as the save itself. Auto-save, click-to-apply
Spacing, Grid & Layout, Borders, Shadows, Icons Auto-saves on every edit, but has no live-apply path at all today - shell.js exposes no window.ADS_apply* for these sections, so a saved value only ever surfaces in this page's own preview, Machine View and Markdown/token export, never in how the rest of the site actually renders. Tracked as a known gap, not hidden behind "Save" language that implies otherwise. Auto-save, export-only

Rollback: every section above its own list has a "Reset to defaults" button that clears its localStorage key and, for the auto-apply and click-to-apply tiers, removes the live CSS override too - there's no separate undo-last-edit, resetting is the one rollback path everywhere.

Storage recovery matrix: all 8 editors' auto-save now goes through one shared window.ADSStorage (shell.js) instead of calling localStorage directly, so every failure mode below behaves the same way everywhere instead of depending on which section you're on:

Write fails (quota exceeded, storage unavailable) The error is caught instead of thrown uncaught mid-click - your on-screen selection can still change, but a visible banner says the change may not have persisted, and the field's previous saved value (if any) is left exactly as it was, since a failed write never reaches localStorage at all. Caught, reported, old value kept
Read fails or the record is corrupt JSON Falls back to this section's own documented default - same as "nothing was ever saved" - but now says so with a visible banner, instead of silently defaulting with no sign your prior save was lost. Falls back, reported
Record from a future/unrecognized schema Named gap, not yet built: unlike the project profile (project-model.js, which already rejects a newer app version instead of misreading it), these 8 editors' own saved shapes carry no version stamp today - none has changed shape since it was introduced, so there's no real migration to demonstrate yet. Tracked as its own follow-up, not papered over here. Not yet versioned

Foundation release contract

The checks above are shared across every Foundation. This is the section-specific half: what counts as a compatible vs. breaking change to that section's own tokens, how a removed/renamed value gets deprecated instead of silently breaking saved projects, and what evidence closes a change as release-ready. One team (Design System Team) owns all nine sections today - a legitimate choice at this system's current size, not a gap - so "owner" isn't repeated per row below.

Colors Additive: a new semantic alias. Breaking: a renamed/removed CSS custom property - deprecate by keeping the old variable as an alias for one release instead, noted in CHANGELOG.md. Release-ready when: contrast badges recompute correctly, Dark Mode sync holds across all 4 sections, and the full-site regression sweep is clean. Alias, don't remove
Grid & Layout Additive: a new product card or layout pattern. Breaking: a changed data-product slug or grid-type key - deprecate by keeping the old slug as an entry in PROJECT_PRODUCT_TYPE_MAP rather than deleting it outright. Release-ready when: the New Project to Spacing/Radius/Grid & Layout sync matrix passes for every category and the regression sweep is clean. Keep slug mapped
Typography Additive: a new semantic level or platform preset. Breaking: a renamed font-size/weight token - deprecate by migrating a saved profile's per-level state on read, the same pattern project-model.js already uses for product-type migration. Release-ready when: a profile saved under the prior shape still loads and renders without error. Migrate on read
Spacing Additive: a new product card. Breaking: a renamed system key (2px/4px/8px/Adaptive) or data-product slug - deprecate by aliasing the old slug/key rather than removing it. Release-ready when: the same 3-page product/platform sync matrix as Grid & Layout passes. Alias, don't remove
Radius Additive: a new philosophy. Breaking: a numeric token's meaning changing without its name changing - deprecate by renaming rather than reassigning a numeric token's value, since a token name must keep meaning the same thing. Release-ready when: a section's Machine View value matches the live computed CSS custom property it claims to represent. Rename, don't reassign
Borders Additive: a new preset. Breaking: a state's property becoming fixed after being advertised as editable - deprecate an editable property by relabeling it fixed in the same release the UI control is removed, not after. Release-ready when: every input the Config panel exposes actually changes what Save persists. Relabel same release
Shadows Additive: a new elevation layer. Breaking: a philosophy's resolved recipe changing without its name changing - deprecate a philosophy by keeping its name mapped to a new recipe only with a CHANGELOG note, never silently. Release-ready when: a Machine View's resolved value matches the live rendered box-shadow. Note recipe changes
Icons Additive: a new library. Breaking: an uploaded/custom icon reference no longer resolving - deprecate a library by keeping its id resolvable even once no longer offered as a default choice. Release-ready when: an uploaded icon still resolves after a reload, not only within the same session (tracked separately as a known gap today). Keep id resolvable
AI & Agents Additive: a new rule or example. Breaking: a demo's cited evidence no longer matching its named source - deprecate an example by removing it in the same release its citation stops matching, not leaving a stale one live. Release-ready when: every citation in this section has been re-checked against the real file/line it names. Re-check citations
